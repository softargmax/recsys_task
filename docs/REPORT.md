# Нейросеть как инженер признаков: обучаемая грамматика агрегатов для ранжирования на Yambda-50M

Отчёт по заданию T-Bank RecSys: «автоматизировать построение признаков или найти альтернативу сильному бустингу на ручных признаках».

## Коротко

- **Идея.** Почти все ручные признаки по истории (сколько раз слушал артиста за 7 дней, доля дослушиваний трека за месяц, доля скипов за последние 3 трека) — это частные случаи одной формулы: `сумма по истории (событие) x (ядро по времени) x [связь с кандидатом]`. Мы задаём оси этой формулы как явную грамматику, а конкретные признаки выбирает градиент, а не человек и не перебор. Каждый выученный признак записывается обычной фразой и передаётся в CatBoost как колонка.
- **Результат.** 32 выученных признака по истории дают CatBoost **+0.0031 GAUC** [0.0016; 0.0046] против 64 ручных. Это среднее по 5 сидам, парный перестановочный тест по пользователям даёт p = 1.2e-4 с поправкой Холма. 64 выученных признака обходят ручной набор **по всем трём метрикам**: GAUC +0.0034, NDCG@10 +0.0028, LogLoss −0.0005. Вместе с ручными признаками выигрыш **+0.0043 GAUC, +0.0035 NDCG@10, −0.0018 LogLoss**, все разницы значимы.
- **Против перебора.** При равном числе признаков градиент обходит отбор по важности на +0.013–0.017 GAUC. 32 выученных признака дают то же качество, что все 822 кандидата перебора.
- **Что дало прирост.** Абляция алфавита показала, что весь разрыв со старым алфавитом закрывает один канал: **непрерывная доля прослушанного**. Бинарные события «дослушал / скипнул» совпадают с меткой и теряют информацию.
- **Цена.** Строить базис в ~10 раз дороже, чем ручные признаки. Плотный слой требует в 25 раз больше состояния на пользователя. После обрезки до трети базиса памяти нужно в 5 раз меньше, а выигрыш сохраняется. Вариант, в котором каждый признак ровно совпадает со своим описанием словами, даёт качество ручного набора при 1.8× памяти. Это проверка интерпретируемости на деле, а не по виду весов.

| | Признаков по истории | Test GAUC | LogLoss | NDCG@10 |
|---|---|---|---|---|
| без истории (только трек, контекст, лайки) | 0 | 0.5735 | 0.5510 | 0.7859 |
| перебор: top-32 по важности CatBoost | 32 | 0.7525 | 0.3295 | 0.8277 |
| ручные признаки (сильный бейзлайн) | 64 | 0.7545 | 0.3286 | 0.8314 |
| **градиент: `grammar32`** | 32 | **0.7576** | 0.3292 | 0.8327 |
| **градиент: `grammar64`** | 64 | **0.7583** | **0.3282** | 0.8341 |
| **ручные + 32 выученных** | 96 | **0.7592** | **0.3269** | **0.8347** |

Ручные признаки и `grammar32` даны средним по 5 сидам (прогон `seeds`), `grammar64` и гибрид — средним по 3 сидам (прогон `scale`). Перебор и строка без истории — один сид из прогона `discovery`.

## 1. Постановка

**Данные.** Yambda-50M (Яндекс Музыка): 10 тыс. пользователей, 47.8M событий (прослушивания, лайки, дизлайки), вся история каждого пользователя без сэмплирования. EDA лежит в `notebooks/01_eda.ipynb`.

**Объект и метка.** Объект — прослушивание, которое включил рекомендатель (`is_organic = 0`). Это аналог показа. Метка: пользователь дослушал хотя бы половину трека (`played_ratio_pct >= 50`). Скипы логируются, поэтому негативы настоящие, а не сэмплированные. Органические прослушивания (пользователь сам нашёл трек) в таргет не входят и используются только как признаки.

**Разбиение по времени.** Отсчёт от конца датасета: train 28 дней (2.75M объектов), val 7 дней (0.73M), test 7 дней (0.73M). Неделя на val и test покрывает недельный цикл: каждый 7-й день трафик ниже на 15%. Признаки, их состав и гиперпараметры выбираются только по val. Затем модель переобучается на train+val с числом итераций `1.15 × best_iteration`, и test оценивается один раз.

**Важная деталь данных.** `timestamp` прослушивания — это момент **конца** прослушивания. Мы это проверили: разница между соседними событиями совпадает с длительностью следующего прослушивания с точностью до 3.6 с по медиане. Поэтому момент запроса — конец предыдущего прослушивания пользователя. Наивный признак «время с прошлого события» равен длительности текущего прослушивания, то есть метке, и один даёт AUC 0.81. Такой признак запрещён.

**Метрики.**
- LogLoss и AUC по всем объектам;
- GAUC — AUC внутри пользователя, взвешенный по числу объектов. Это главная метрика ранжирования;
- NDCG@10 внутри групп «пользователь × день»;
- все метрики отдельно по срезам новизны: повтор трека, новый трек знакомого артиста, новый артист;
- интервалы — bootstrap по пользователям, значимость — парный перестановочный тест по пользователям (раздел 4.3).

**Защита от утечек.** Тест «отрезанного будущего»: признаки пересчитываются на данных, обрезанных в середине валидации, и для объектов за сутки до обрезки должны совпасть бит в бит. Тест пройден по всем 584 признакам. Специально добавленная признак-канарейка (`played_ratio` следующего события) тестом ловится. Признаки трека и артиста — снимок на начало суток. CF-факторы обучены по истории до начала train. Код в `rank/leakage.py`.

## 2. Сильный бейзлайн

CatBoost (`depth 8`, `lr 0.08`, ранняя остановка по val) на ручных признаках. Группы признаков:
- **пользователь:** активность и доля дослушиваний в окнах 1ч / 1д / 7д / 30д / всё, доля органики, открытость к новым артистам;
- **трек, артист, альбом:** популярность и сглаженная доля дослушиваний, снимок на начало суток;
- **пара с треком:** повторы в окнах, давность, исход последнего прослушивания, лайк на момент запроса;
- **пара с артистом и альбомом:** то же для косвенных связей;
- **сессия и контекст:** позиция в сессии, исходы последних 1 / 3 / 10 треков, доля прослушанного у прошлого трека, час, день недели;
- **CF:** SVD-факторы и похожесть кандидата на последние треки.

Test GAUC: «лестница» из прогона `ladder`, 1 сид.

| Модель | Признаков | GAUC | LogLoss |
|---|---|---|---|
| логистическая регрессия на 17 главных признаках | 17 | 0.7127 | 0.3625 |
| CatBoost, ручные окна (L0) | 88 | 0.7534 | 0.3290 |
| CatBoost, + CF (опорный набор `human`) | 94 | 0.7548 | 0.3286 |
| CatBoost, окна заменены экспоненциальным затуханием с 5 tau (L1) | 116 | 0.7557 | 0.3283 |

Абляция групп: без контекста сессии GAUC падает на 0.052, это самая важная группа. Важность по масштабам совпадает с EDA: у пользователя доминирует tau = 1 ч, у пары с треком — 90 дней.

## 3. Метод: обучаемая грамматика признаков

### 3.1. Грамматика

Ручной признак — это сумма по прошлым событиям пользователя:

```
feature = sum_j  atom(j) * kernel(j) * [relation(j, кандидат)]
```

Оси грамматики («алфавит»):

| Ось | Значения |
|---|---|
| связь | любой трек; тот же трек; тот же артист; тот же альбом; CF-похожие треки (вес — косинус SVD-векторов, последние 64 события) |
| событие (атом) | рекомендация / органика × дослушал / скипнул; **доля прослушанного**; дослушал / скипнул трек нового для себя артиста |
| ядро | последние 1 / 3 / 10 треков; текущая сессия; экспонента с tau 1ч / 6ч / 1д / 3д / 7д / 30д / 90д; вся история; давность последнего события связи (затухание 1д и 30д) |

5 связей × 7 событий × 14 ядер = **490 базисных сумм** на объект. Они считаются за один проход сортировкой и префиксными суммами. Экспоненциальные суммы считаются в лог-пространстве через `logaddexp.accumulate`, `O(n log n)` по числу событий. Код: `rank/basis.py`, `rank/windows.py`. Базис проверен двумя способами: совпадение с наивным пересчётом и точное воспроизведение ручных признаков (позиция в сессии, доля прослушанного у прошлого трека, давность трека).

### 3.2. Обучаемый слой

Слой строит K признаков. У каждого признака есть:
- распределение по связям (softmax);
- распределение по ядрам (softmax);
- веса событий в числителе (sigmoid) и в знаменателе (не меньше числителя).

Половина признаков — счётчики `log1p(числитель)`, половина — доли `(числитель + 0.5) / (знаменатель + 1)`. Слой обучается вместе с MLP-головой на logloss, около 2 минут на T4. Небольшой штраф на энтропию делает выбор связи и ядра почти дискретным. Затем K признаков передаются в CatBoost как обычные колонки, и **финальной моделью остаётся бустинг**. Код: `rank/learned.py`.

Пример выученных признаков (`grammar32`, первые места по важности CatBoost):

```
count: скипы + доля прослушанного по любым трекам, последние 3 трека     -> как прошли последние треки
rate:  ... по тому же треку, затухание 30 дней                            -> отношение к этому треку за месяц
count: скипы, особенно у новых артистов, последние 10 треков
count: доля прослушанного по тому же треку, текущая сессия               -> сколько этого трека уже прослушано сейчас
rate:  ... по CF-похожим трекам, текущая сессия                           -> реакция на похожее в этой сессии
```

### 3.3. Чем это отличается от известного

Отдельные части уже встречались:

| Компонент | Где уже есть |
|---|---|
| агрегаты по связям и их перебор | Deep Feature Synthesis (2015), OpenFE (2022) |
| экспоненциальные счётчики как потоковые признаки | стандартная индустриальная практика |
| обучаемые временные ядра по связям | SLRC+ (WWW 2019), Chorus (SIGIR 2020), но там они часть модели факторизации, а не признаки для бустинга |
| непрерывная релаксация дискретного выбора через softmax | DARTS (2018), поиск архитектур нейросетей |
| дифференцируемый поиск признаков для табличных данных | DIFER (2020), но с универсальными арифметическими операциями, а не с агрегатами по истории |

Что мы делаем иначе: ручной feature engineering рассматривается как параметрическое семейство, параметры которого **обучаются, а не перебираются**. На выходе получаются **читаемые** признаки для бустинга, а не новая модель вместо него. Мы не нашли работы, где выученные таким образом агрегаты прямо сравниваются с сильным бустингом на ручных признаках при одинаковых данных, объектах и метриках.

## 4. Эксперименты

Все сравнения сделаны на одном разбиении, одних объектах и одной общей части признаков `fixed`: трек, артист, альбом, лайки, контекст, SVD-скор. Наборы отличаются только признаками по истории. Все числа ниже пересчитываются по артефактам в `outputs/`, команды есть в README.

### 4.1. Человек против перебора против градиента

Перебор устроен в духе OpenFE: все базисные суммы и доли из той же грамматики (822 кандидата), CatBoost на всех, отбор top-K по важности. Test GAUC, 1 сид:

| K признаков по истории | случайные | перебор, top-K | градиент, `grammarK` | слой без бустинга |
|---|---|---|---|---|
| 8 | | 0.7347 | **0.7519** | 0.7432 |
| 16 | 0.6566 | 0.7400 | **0.7525** | 0.7462 |
| 32 | | 0.7525 | **0.7574** | 0.7492 |
| все 822 | | 0.7545 | | |
| ручные, 64 | | | 0.7549 | |

- **Перебор проигрывает,** потому что ранжирует признаки поодиночке. 15 из его top-16 описывают одно и то же: статистику пользователя на соседних окнах. Слой учит признаки совместно и сам разносит их по связям и масштабам.
- **Слой без бустинга** слабее CatBoost на тех же признаках. Его роль — генератор признаков, а не замена бустинга.

### 4.2. Алфавит важнее способа поиска

Первая версия алфавита имела 4 бинарных события и 11 ядер, без доли прослушанного, сессии и давности. С ней `grammar32` отставал от ручных признаков на 0.016 GAUC (0.7386 против 0.7549), и гибрид почти ничего не давал. Расширение алфавита закрыло разрыв. Абляция показывает, какой канал за это отвечает. `grammar32`, 2 сида:

|---|---|---|---|
| полный | 0.7571 | | |
| старый + только доля прослушанного | **0.7572** | +0.0001 | 1.0 |
| полный без сессии | 0.7563 | −0.0008 | 0.40 |
| полный без давности | 0.7562 | −0.0009 | 0.40 |
| полный без новых артистов | 0.7571 | 0.0000 | 1.0 |

Канал «новые артисты» давал признаки из топа важности CatBoost, но абляция показала, что он ничего не добавляет. Важность признака не равна его вкладу.

### 4.3. Устойчивость и значимость

Слой и CatBoost переобучены на **5 сидах**, сид меняется у всех моделей, включая ручную. Тест — **парный рандомизационный тест со сменой знака по пользователям**, 100 000 перестановок, двусторонний:
- пользователь — единица наблюдения, потому что объекты одного пользователя зависимы;
- каждая метрика раскладывается на вклады пользователей;
- α = 0.05, поправка Холма на 9 гипотез;
- мощность 0.8 (β = 0.2) задаёт минимально детектируемый эффект MDE.

Код: `rank/stats.py`.

| Против ручных | GAUC [95% CI] | p (Холм) | MDE | NDCG@10 | LogLoss |
|---|---|---|---|---|---|
| `grammar32` | **+0.0031 [0.0016; 0.0046]** | 1.2e-4 | 0.0021 | +0.0013, p 4e-4 | +0.0005 (хуже), p 1e-4 |
| ручные + 16 выученных | **+0.0035 [0.0026; 0.0044]** | 9e-5 | 0.0012 | **+0.0026**, p 9e-5 | **−0.0014**, p 9e-5 |
| слой без бустинга | −0.0028 [−0.0043; −0.0013] | 2e-4 | 0.0022 | −0.0024 | +0.0036 |

- `grammar32` выигрывает на каждом из 5 сидов по отдельности: от +0.0022 до +0.0034. Разброс между сидами (std 0.0003–0.0006) в 4–9 раз меньше эффекта.
- По срезам новизны `grammar32` не хуже ручных нигде. Сильнее всего он выигрывает на новых треках знакомого артиста.
- Разные сиды находят функционально те же признаки: средняя максимальная корреляция 0.83. Точное ядро при этом может отличаться (соседние tau взаимозаменяемы), поэтому признаки стоит описывать по смыслу, а не по точному tau.

- **Обрезка до трети базиса почти бесплатна:** при 162 ячейках качество не меняется, а выигрыш над ручными остаётся значимым. Памяти нужно в 5 раз меньше, чем плотному слою.
- **«Читаемый» вариант** — каждый признак ровно такой, как написан словами, одна связь и одно ядро — **даёт качество ручного набора** при 1.8× памяти. Признаки, найденные автоматически, полностью интерпретируемы и заменяют ручную работу.
- **Время на событие растёт линейно:** части данных обрабатываются за одинаковое время.
- **Дискретное обучение не помогло.** Жёсткий выбор связи и ядра со straight-through-градиентом (`rank/sparse.py`, 3 сида) даёт 0.7554 GAUC, то есть +0.0007 к ручным, незначимо. Это на уровне «читаемой» обрезки. Выигрыш плотного слоя создают смеси нескольких ядер и связей в одном признаке, а не отдельные ячейки.

## 5. Что сработало и что нет

**Сработало**
1. **Градиентный поиск в явной грамматике** находит признаки лучше перебора при любом бюджете и лучше человека при половине числа признаков. При равном числе признаков (64) он лучше по всем трём метрикам. Выигрыш значим и устойчив к сиду.
2. **Выученные признаки дополняют ручные:** гибрид лучше по всем трём метрикам. Значит, слой нашёл информацию, которой нет в ручном наборе. По абляции это в первую очередь доля прослушанного, агрегированная по связям и ядрам, которых у человека нет: тот же трек в сессии, CF-похожие треки, короткие окна.
3. **Анализ через абляцию алфавита** отвечает на вопрос, какой компонент даёт прирост. Отбор по важности здесь вводит в заблуждение.

**Не сработало или сработало частично**
1. **Первая версия алфавита** с бинарными событиями проигрывала человеку на 0.016 GAUC. Метод хорош ровно настолько, насколько хорош алфавит.
2. **Слой как самостоятельная модель** уступает CatBoost на 0.003 GAUC.
3. **Калибровка при малом K:** `grammar32` чуть хуже ручных по LogLoss (+0.0005). При K = 64 это уходит: LogLoss −0.0005 к ручным, значимо.
4. **Читаемость слоя частично иллюзорна.** Веса выглядят дискретными (1.00 после округления), но CatBoost использует хвост, и после обрезки без переобучения качество падает. После переобучения «читаемый» вариант сравним с ручным набором, но теряет 0.0026 GAUC относительно плотного.
5. **Память.** Плотная грамматика требует в 25 раз больше состояния на пользователя, чем ручные признаки.

## 6. Ограничения

- **Офлайн-оценка по логам.** Мы переранжируем то, что уже выбрала старая рекомендательная политика, и ничего не можем сказать о треках, которые не показывались.
- **Один датасет и одна постановка** (дослушивание рекомендации). На KION или другой цели метод не проверялся.
- **Алфавит задаёт человек.** Метод автоматизирует выбор признаков внутри грамматики, но не изобретение новых осей. Абляция показывает, как проверить, нужен ли новый канал.
- **Перебор `brute_all` на 822 колонках** обучен на выборке 1M строк, потому что иначе не помещается в память Kaggle. Наборы top-K обучены на полных данных.
- **Последовательные модели** (трансформер по истории) и **графовые модели** как альтернатива бустингу не делались. Мы сознательно остались в рамках «автоматизации признаков для бустинга».
- **Память на пользователя** — оценка по формуле, а не замер в реальном сервинге.

## 7. Воспроизведение

Весь код в `rank/` и `scripts/`. Kaggle-ноутбуки генерируются из того же кода командой `kaggle/build_notebook.py <stage>`, код вставляется ячейками `%%writefile`. Команды приведены в `README.MD`.

| Этап | Kaggle-ноутбук | Артефакты |
|---|---|---|
| признаки и проверка утечек (CPU, один раз) | `rabochi1024/yambda-features` | кэш для остальных ноутбуков |
| бейзлайн и лестница L0–L1 | `rabochi1024/yambda-catboost-baseline` | `outputs/kaggle_v2` |
| человек / перебор / градиент | `rabochi1024/yambda-feature-discovery` | `outputs/kaggle_discovery_base`, `outputs/kaggle_discovery_rich` |
| 5 сидов и стат-тесты | `rabochi1024/yambda-grammar-seeds` | `outputs/kaggle_seeds_v2` |
| абляция алфавита | `rabochi1024/yambda-grammar-ablation` | `outputs/kaggle_ablation` |
| обрезка весов и «читаемый» вариант | `rabochi1024/yambda-grammar-prune` | `outputs/kaggle_prune` |
| дискретная грамматика | `rabochi1024/yambda-grammar-sparse` | `outputs/kaggle_sparse` |
| K = 32 / 64 и гибриды | `rabochi1024/yambda-grammar-scale` | `outputs/kaggle_scale` |
| затраты, локально | `scripts/cost_report.py` | `outputs/cost` |

Модели CatBoost (`models/*.cbm`), веса слоя (`grammar/*.pt`), выученные признаки словами (`grammar/features_k*.md`), предсказания на test и стат-тесты лежат в папках артефактов. Стат-тест пересчитывается локально по сохранённым предсказаниям:

```
python3 scripts/stat_tests.py outputs/kaggle_seeds_v2/outputs/test_predictions.parquet --models grammar32 human+grammar16 grammar_nn32
```
